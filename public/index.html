RECORRIDO DEL PROYECTO

¿Qué hicimos?

Construimos un flujo para analizar pedidos históricos de una empresa que vendía en varios países. Usamos Scrapy para recolectar información de la web, limpiamos y cruzamos los registros con Python, y usamos los datos resultantes para construir el informe de Power BI y esta web.

El objetivo fue entender cómo evolucionaron las ventas, dónde se concentraron y qué aportaron los clientes y las categorías de producto.

01

¿Cómo obtuvimos los datos?

El spider de extract_kaggle.py hizo peticiones web, leyó el HTML y guardó los resultados de la extracción.

Kaggle · ficha del dataset y pedidos

  1. Scrapy abrió la página de Sample Sales Data y leyó el bloque de metadatos application/ld+json incrustado en el HTML.
  2. De ese bloque obtuvo título, autor, licencia, versión y tamaño del ZIP publicado.
  3. Descargó el ZIP de Kaggle, contrastó el tamaño anunciado y extrajo sales_data_sample.csv. Las líneas de pedido están en ese archivo.
Ver la ficha de Kaggle

ONU · clasificación geográfica M49

  1. Scrapy recorrió las filas HTML de las tablas M49 en inglés y español.
  2. Leyó las celdas con país, región, subregión y códigos ISO. Unió ambas tablas por ISO alfa-3 y guardó el resultado en un_m49_countries.json.
  3. El ETL usó ese JSON para asignar una región geográfica a los países del CSV de ventas.
Ver las tablas web de la ONU

¿Qué limpia y transforma el ETL?

Resumen de lo que hace etl.py con los datos antes de cargarlos.

QUÉDETALLE
TiposFechas de 1/6/2003 0:00 a 2003-01-06; cantidades, precios e importes de texto a números.
EspaciosQuita espacios sobrantes en los textos.
ColumnasDescarta 8 de las 25 columnas, porque ningún análisis las usa: teléfono, dos de dirección, nombre y apellido de contacto, y las columnas de trimestre, mes y año.
Campos nuevosAño, mes, período, grupo de estado, región comercial y la brecha frente al precio de lista.
EstructuraArma las tablas de clientes, productos, países y regiones.
ValidaciónRevisa duplicados, campos vacíos, cantidades no positivas, ventas negativas, fechas inválidas, países sin región y llaves rotas.

Resultado: filas de entrada → salida — · filas eliminadas —. La fuente ya venía limpia: el ETL estandariza, valida y enriquece más de lo que corrige.

También derivamos discount_proxy comparando el precio unitario con el MSRP. Este campo mide una brecha de precio y sirve para explorar su relación con las unidades compradas.

Ejecutar el ETL desde el proyecto

etl/etl.py cruza tres tipos de fuente: el CSV de pedidos, los JSON (regiones M49 de la ONU, territorios comerciales y códigos ISO) y un script SQL con la clasificación de los estados. Después valida la calidad y carga retail_sales.db y los CSV para Power BI.

python etl/etl.py
python etl/compare_processed.py data/processed <carpeta-nueva>
  • Si falla un control (duplicados, ventas negativas, fechas inválidas, un país sin región M49…) el ETL se detiene y no modifica los resultados anteriores.
  • Con el CSV recién extraído, el ETL reproduce exactamente las tablas, el resumen y el ANOVA ya validados; compare_processed.py lo comprueba tabla por tabla.
Ver etl.py

Cómo llegan los datos a esta web

La API de Node.js lee SQLite en solo lectura, agrupa las filas según la selección y envía totales y otros indicadores al navegador. La interfaz los presenta como tablas y gráficos interactivos.

Por ejemplo, el punto 6 muestra el promedio por territorio comercial y por región M49. Así puedes ver dónde se usaron los datos de la ONU obtenidos mediante scraping.

Comparamos el importe promedio por línea de pedido entre las categorías de producto. La hipótesis inicial fue que todas las categorías tenían la misma media.

ANOVA clásico de una vía
